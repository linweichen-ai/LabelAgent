# 点提示上下文竞态修复：Round 212

## 一句话结论

点提示请求现在会在提交瞬间冻结数据集、相机、帧、类别和点位；生成期间不能继续改点、撤销或清空。如果页面在响应回来前切换了数据集、相机或帧，旧结果会被明确丢弃，不能落入新数据。真实 Edge 验收验证：连续调用两次只发送一次；生成期间把类别从 `pallet` 切到 `person`，返回候选仍绑定提交时的 `pallet`；切换数据集路径后旧候选没有进入新上下文。

## 本轮发现的真实问题

Round 211 已在服务端合并完全相同的并发点请求，但继续审计浏览器源头时发现两个独立竞态：

1. 旧实现只冻结 frame 和 topic，响应回来后才读取类别下拉框。如果用户等待时切换类别，旧掩码会被错误标成新类别。
2. 旧实现没有绑定数据集路径。如果切到另一个数据集后恰好 topic 和 frame 相同，旧结果有机会显示在新数据上。

另外，生成期间画布仍可加点，撤销和清空按钮也仍可执行。底层请求已经发送，但页面的提示点计数可能被之后的操作改变，造成“界面看起来这些点已参与、实际模型没有收到”的错觉。

## 修复方式

提交点提示时冻结以下字段：

- `loadedDataPath`：当前数据文件；
- `topic`：当前相机；
- `frame`：当前帧；
- `requestLabel`：提交时类别；
- `requestPoints`：逐点数值深拷贝。

响应回来后必须同时满足数据文件、相机和帧仍一致才允许显示。类别始终使用提交时类别；若等待期间类别发生变化，候选仍按原类别生成，并明确提示复核人重新确认。生成期间以下操作会直接提示并保持现状：

- 再次进入 SAM 点选；
- 切换多边形或正负点模式；
- 在画布继续加点；
- 撤销提示点；
- 清空本帧。

服务端 Round 211 的精确 in-flight 合并继续保留，作为多标签页和网络重试的第二层兜底。
