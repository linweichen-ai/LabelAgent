# `other_robot` 自适应复核与长路径修复：Round 199–202

## 一句话结论

直接把不同图像数量的 VLM 请求硬合批，调用次数虽然少了，但反而更慢，已否决并从代码移除。随后改成“先做基础分类，只让机器人、叉车、未知物体和工具设备进入第二遍正例参考复核”，四张跨序列图的最终分流与完整双遍一致，VLM 分类读数降低 23.63%，批次调用减少 31.25%。这一能力仍是离线候选，不是生产部署或准确率结论。

## Round 199：先暴露并修复 Windows 长路径问题

第一次运行在保存候选图时失败，模型尚未形成结论。根因不是 SAM/VLM 离线，而是静态样本 ID 同时出现在父目录和文件名中，完整路径超过 Windows 常规路径长度。

修复方式：

- 短帧号继续保留原值，例如第 74 帧仍使用 `74`；
- 过长的静态样本 ID 改成 `id-<12位SHA-256>` 文件名令牌；
- 父目录仍保留完整样本 ID，结果 JSON 仍保存原始 ID，所以可追溯性没有丢失；
- 失败产生的局部临时目录在确认位于本仓库 `artifacts` 根目录后精确删除。

修复后使用同一长输出目录重跑成功。该次结果 SHA-256 为：

`70b2986d4602baa7f00355861a466dcb7b839d89779ae30580bdccaa39b55d92`

这次重跑还发现旧脚本的分项计时与外部等待时间不一致，因此没有采用其速度数字。后续改为进程内单调计时，并新增完整运行耗时字段。

## Round 201：异构尾部合批失败

尝试把原来两个单候选尾部请求合并成一个两行批次。其中一行只看候选图，另一行同时看候选图和正例参考图。最终分流没有改变，但速度明显退化：

| 指标 | Round 200 | Round 201 | 变化 |
|---|---:|---:|---:|
| VLM 调用批次 | 16 | 12 | 减少 25% |
| VLM 分类计时读数 | 51.810 秒 | 84.356 秒 | 增加 62.82% |
| 完整运行计时读数 | 97.835 秒 | 133.263 秒 | 增加 36.21% |

原因是不同提示长度、不同图片数量被放进同一批次后，需要按最重的一行补齐和解码；“请求更少”不等于“GPU计算更少”。该方案已否决，相关运行代码已经移除，不会成为隐藏的慢路径。结果 SHA-256：

`df1dfca00b058791305d3932d3303514cc73f69177b22c308a2211c7e34c2aa3`

## Round 202：自适应正例参考复核

新方案先做一次基础分类，只有以下四类候选才进入第二遍：

- `other_robot`：需要正例参考确认；
- `vehicle_or_forklift`：需要区分普通人工叉车和无人平台；
- `unknown_object`：证据不足，不能直接丢弃；
- `tool_or_equipment`：小型工业设备容易与机器人混淆。

明显的托盘、人物、地面结构、自车部件等不再重复做正例参考复核，而且“跳过第二遍”永远不能晋级为自动候选。

## 安全边界

- 自适应逻辑只减少不必要的第二遍复核，不降低自动晋级标准；
- 没做正例参考复核的候选强制 `dual_pass_consensus=false`；
- 助理预审仍不是人工真值，分流一致不能称为准确率；
- 没有写入正式状态、人工真值、训练批准或生产权重；
- 35/35 项相关与边界测试通过，Python 编译和差异检查通过；
- 收尾时工作台、两路 SAM 与 VLM 均为 HTTP 200，SAM/VLM 进行中请求和等待请求均为 0；
- 正式 `state.json` 与 `file_sessions.json` 哈希与 Round 198 记录一致。
