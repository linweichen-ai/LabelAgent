# 单卡 8GB 本机运行

## 运行方式

使用独立的 Qwen3-VL-2B 环境，以 bitsandbytes NF4 加载语言部分，视觉模块保留较高精度。模型文件来自 Qwen 官方仓库，按固定版本和官方 SHA256 校验；下载完整权重后在加载时量化。实际是否量化成功由 `is_loaded_in_4bit` 检查，不能以文件名判断。

工作台继续使用原端口；单卡管理器保持两个对外接口在线，并在请求到来时启动需要的模型：

| 接口 | 本地端口 | 用途 |
| --- | --- | --- |
| 工作台 | 8765 | 保持原有数据和交互 |
| SAM3 管理入口 | 8766 | 转发文本、点提示分割 |
| VLM 管理入口 | 18868 | `/v1/chat/completions`、模型探测 |
| SAM3 子进程 | 17866 | 管理器按需启动 |
| VLM 子进程 | 18869 | 管理器按需启动 |

管理器等待旧模型进程树退出后才启动下一个模型。Windows 虚拟环境启动器和真正的 Python 子进程都纳入退出检查；仅终止它自己创建的进程。Windows Job 机制确保管理器退出时所属子进程也退出，不结束桌面或其他应用进程。

`/health` 和 `/v1/models` 本身不加载模型。连接检查工具在探测真实模型前通过 `/activate` 加载 VLM，后续工作流的模型请求自动触发轮换。管理器串行处理请求，忙碌时明确返回错误。

## 部署

已有 SAM3 环境保持原样。另建 VLM 环境，安装匹配显卡的 CUDA PyTorch/torchvision 和 `tools/requirements-local-gpu.txt`。本轮 Windows 环境使用独立虚拟环境，通过只读的包路径复用原有 PyTorch，新增依赖只装入 VLM 环境；两套环境均通过 `pip check`。

关闭原 SAM3 服务之前，先确认工作台空闲、状态已备份、原端口确由本项目服务占用。保留工作台，使用明确路径启动：

```sh
python tools/local_gpu_manager.py --sam-python <sam-python> --vlm-python <vlm-python> --model-dir <verified-model-directory> --gpu-uuid <local-GPU-UUID>
```

所有接口只绑定本机回环地址。管理器日志、事件及子进程日志保存在 `work/local_gpu_manager/`，不提交到 Git。`/manager/status` 可查看当前模型、所属进程数量及切换事件。采样显存信息与模型真实推理结果须在运行后另行报告。

VLM 使用 `local-8gb` 资源配置，要求选定 GPU 至少有 8GB 总显存和 3500 MiB 可用余量，并显式启用 NF4；Windows 显示进程不自动判定为冲突。此配置不能当作共享 4090 的分配规则，后者继续使用原有严格占用检查。

密集参考的坐标文本会压缩为范围和顶点数，参考图仍带完整轮廓；这避免原始坐标挤满上下文，原轮廓数据不变。规范描述和每轮复核均使用原图及单独的洋红色轮廓参考，避免着色改变物体外观。描述输入版本已更新，旧描述须重新准备。

使用 [独立验收入口](local-vlm.md) 执行真实规范生成 → SAM3 分割 → VLM 复核 → 工具修改（如有依据）→ 再观察。所有轮廓、调用和候选预览写入新目录，不写原参考标注或生产真值。

模型连通、流程完成、发生多轮修改、像素准确率是不同的结论，分别记录。当前阶段见 [进度记录](test-results/local_gpu_progress.json)，最终结论以真实运行汇总为准。
