# Round533：已加载工作区即时恢复与状态快照门禁

## 目标

继续解决“工作台能打开，但首次进入或已有数据恢复时不够丝滑”的问题。本轮只优化网页恢复、状态读取和只读验收，不启动真实推理、训练、微调或后训练，也不写候选、审核记录或人工真值。

## 从失败证据定位问题

Round532 正式页面在没有恢复数据时可以稳定通过空闲验收；但恢复已有数据后，首轮隔离 Edge 验收出现 5 次 `/api/run/status`，超过 4 次旧预算。进一步记录浏览器调用来源后确认：

- 主工作台、工作区恢复和相邻帧预取可能在启动阶段分别读取状态；
- 已有空闲快照没有时间和数据作用域门禁，理论上可能在另一任务已经运行时误触发一次预取；
- 初次状态已经正确时，工作区仍可能等待下一次 15 秒轮询才发出“恢复完成”；
- 旧验收把启动期和稳定期混在一起，也没有拦截全部同源非 GET API，结论不够严格。

独立只读审阅首先指出了“陈旧 idle 快照”和“非 GET 守门不完整”两项高优先级问题。本轮没有直接接受审阅结论，而是逐项在源码、后端拒绝路径和真实浏览器网络记录中复核后修正。

## 实现

- 主工作台发布运行状态时同时记录观察时间；数据作用域不一致时主动把该时间清零，空闲占位不再能授权预取；
- 相邻帧预取只有在快照不超过 2 秒，并且文件、相机和载入代次全部一致时才复用空闲状态；过期或错作用域时重新读取权威状态；
- 恢复中的短暂错作用域状态一旦重新对齐，会取消遗留的 1 秒恢复计时器并回到正常 15 秒空闲轮询；
- 初次状态已经匹配当前数据时，直接发出工作区就绪，不再等待下一轮 15 秒状态读取；
- 浏览器验收拆分启动期与稳定期计数，稳定期按实际 15/30 秒节奏计算预算；
- 所有同源 `/api/` 非 GET 请求默认判失败，仅显式允许恢复当前相机所需、不会写候选或真值的 `POST /api/topic`，并在回执中单列；
- 调用来源回执仅保留本机同源 pathname 与函数名，删除查询参数、盘符路径和外部来源；
- 原子网页部署清单由 3 个扩为 4 个文件，纳入本轮变化的 `reference-prep.js`，仍保留旧版本校验、备份、读回和失败回滚。

页面候选版本为 UI `171`，资源版本为 app `206`、guide `121`、reference-prep `170`。

## 隔离真实浏览器验收

最终在复制的正式状态索引上恢复已有数据：

| 项目 | 结果 |
| --- | ---: |
| 工作区恢复完成 | 约 1.14 秒 |
| 启动期运行状态读取 | 2 次 |
| 稳定期 32 秒运行状态读取 | 2 次（预算 3） |
| 稳定期 32 秒摘要读取 | 1 次（预算 2） |
| 允许的只读式相机恢复 | `POST /api/topic` 1 次，单独记录 |
| 受保护或未知非 GET API | 0 |
| 外部请求 | 0 |
| HTTP / 页面 / 控制台错误 | 0 / 0 / 0 |

修复前曾出现工作区约 16 秒才恢复；同一隔离状态在补发即时就绪信号后降到约 1.14 秒。这是浏览器实测的页面恢复时间，不等价于模型推理时间提升。
