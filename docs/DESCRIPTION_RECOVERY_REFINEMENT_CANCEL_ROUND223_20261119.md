# 第二百二十三轮：参考描述恢复验收改为真实取消后台精修

日期：2026-11-19

## 通俗结论

上一轮把工作台所有“停止整批任务”操作绑定到了任务号。继续检查配套工具时发现，参考描述自动恢复的浏览器验收脚本还保留着旧写法：它想停止单帧后台精修，却向整批任务停止接口发送了空请求。

这有两个问题：新服务端会拒绝空请求；更重要的是，即使旧服务端返回 HTTP 200，也不代表目标精修真的被取消。验收脚本可能产生“看上去已经停止，实际后台仍在运行”的假象。

现在脚本会读取精修请求本身的唯一编号，并调用精修专用取消接口；服务端回执必须确认已登记取消请求，且帧、相机和精修编号都与原请求一致。

## 发现依据

仓库全局审计发现唯一遗漏位于：

`tools/browser_description_recovery_acceptance.cjs`

旧逻辑在观察到 `/api/reference_candidates/refine` 后：

- 调用 `/api/run/stop`；
- 请求体为 `{}`；
- 只检查 HTTP 状态为 200；
- 没有检查是否实际停止、停止的是哪个任务，也没有绑定精修编号。

整批任务接口和单帧精修接口是两个不同的生命周期。精修专用接口要求 `frame + topic + refinement_id`，并支持“精修已经开始”和“精修即将开始”两种时序：前者直接设置停止信号，后者登记取消意图，由同一精修编号启动时消费。

## 修改内容

脚本现在从 Playwright 捕获到的精修请求中读取：

- `frame`；
- `topic`；
- `refinement_id`。

随后调用：

`POST /api/reference_candidates/refine/stop`

并逐项验证：

1. `refinement_id` 是合法的 32 位 UUID 十六进制形式；
2. HTTP 状态为 200；
3. `cancellation_requested=true`；
4. 回执 `frame/topic/refinement_id` 与原精修请求完全一致；
5. 结果文件额外记录取消是否在当时已经匹配到活动精修。

如果没有观察到延迟精修请求，脚本仍按原逻辑完成描述恢复验收，不伪造取消结果。

## 防回退检查

新增网页测试直接检查正式验收工具：

- 必须读取 `refinementRequest.postDataJSON()`；
- 必须调用 `/api/reference_candidates/refine/stop`；
- 必须携带 `frame/topic/refinement_id`；
- 必须检查 `cancellation_requested=true`；
- 禁止重新出现 `fetch("/api/run/stop")`。

服务端精修取消的活动任务、非相关任务和预先登记取消三种路径，继续由既有 Python 测试覆盖。
