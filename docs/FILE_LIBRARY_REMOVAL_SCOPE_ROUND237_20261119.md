## 通俗结论

工作台文件管理器里的“删除”实际只会把数据从工作台列表移除，磁盘上的 MCAP 或图片不会删除。但旧版本仍有一个真实风险：很久没刷新的标签页可以拿旧列表直接执行移除；如果目标后来变成当前正在看的数据，旧页面还会把工作台卸载，造成画面突然消失。

现在移除操作必须同时证明五件事仍与点击时一致：当前数据文件、当前相机、文件载入代次、整个文件列表版本、目标条目内容与加载状态。任一项已经被另一窗口改变，服务端都会返回 HTTP 409，文件列表、当前画面和磁盘原文件全部保持不变。

## 风险复现与修复范围

### 原问题

原接口 `/api/files/<file_id>` 只依赖 URL 中的文件 ID。旧标签页即使已经落后，也可以：

1. 从当前列表移除目标条目；
2. 如果目标此时是当前数据，保存会话后把工作台置为空；
3. 页面收到旧回执后直接清空本地画面。

该接口不会删除磁盘文件，但会改变正式 `files.json` 和当前工作区，属于需要修复的历史数据管理串台。

### 本轮没有重复修改的部分

- 参考描述生成已经冻结数据、配置、类别、真值、参考帧和内容签名，并在保存前复核；
- 专项复核决定已经绑定清单、原图、斜坡几何和助手建议哈希；
- Round236 已保护类别修改和机器候选清空。

因此本轮只收紧文件列表移除，不给正常推理路径增加等待。

## 实现说明

### 1. 文件列表整体版本

`GET /api/files` 现在返回：

- `library_state_sha256`：原始注册文件列表的 SHA-256；
- `path / topic / file_activation_generation`：读取列表时的当前工作区；
- 每个条目的 `entry_sha256`；
- 每个条目的 `loaded` 与 `available` 状态。

页面只允许基于这一整套快照执行移除。

### 2. 服务端原子校验

移除请求必须携带：

1. `expected_path`；
2. `expected_topic`；
3. `expected_file_activation_generation`；
4. `expected_library_state_sha256`；
5. `expected_file_entry_sha256`；
6. `expected_loaded`。

服务端在同一把状态锁内依次核对工作区、列表哈希、目标条目哈希和加载状态，再更新列表。回执明确包含 `disk_file_deleted: false`，并读回被移除前的列表哈希和目标条目哈希。

### 3. 浏览器不再盲目清空

页面提交时冻结完整绑定；回执必须与提交值完全一致。等待期间页面载入代次发生变化时，旧回执不会卸载新页面。确实移除了当前文件时，浏览器还会重新读取 `/api/bootstrap`：

- 服务器已经切到另一数据：载入服务器当前数据；
- 服务器确实为空：只清空画面，并保留服务器当前载入代次；
- 最后重新读取文件列表，避免并发添加/移除造成显示过期。
