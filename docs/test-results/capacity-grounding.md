# 同输入视觉识别容量对照

目前 2B 视觉复核仍会误拒托盘，示例提示也会接受疑似反光。先固定图片字节、提示、schema 和解码参数，重新运行 2B，再与远端 8B 比较。此阶段诊断模型识别能力，不据此更改工作台候选或原始标注。

## 已完成的真实 2B 基线

8 个自然裁图与 2 个空白对照，每项分别发送单图、裁图加上下文两种请求，共 20 次真实 CUDA 请求。全部收到有效响应，接口确认图片数量；输入 JPEG 未重新编码，20 个请求正文与前一中性提示实验一致，新返回的 20 个类别也逐项一致。

| 样例范围 | 接受 | 拒绝 | 不确定 |
| --- | --- | --- | --- |
| 8 个自然裁图 | 1 | 3 | 4 |
| 其中 5 个目视托盘功能样例 | 1 | 1 | 3 |
| 2 个空白对照 | 0 | 0 | 2 |
| 1 个疑似非托盘样例 | 0 | 0 | 1 |

冻结要求是：全部有效响应、空白不接受、目视托盘不拒绝且至少接受 3 个、疑似非托盘不接受。2B 未通过。功能样例不是独立人工真值，表格不能解释为像素准确率；没有调整要求以掩盖失败。

两模型均使用 NF4、每图 256 个面积 token 预算、温度 0、输出最多 192 token。比较时逐项核对图片摘要与模型别名以外的输入指纹；模型配置摘要单独记录。全部不确定或只完成部分样例均不能通过。原图、裁图及逐项响应留在私有实验目录，仓库只保存 [脱敏基线](vlm_capacity_baseline.json)。

```sh
python tools/evaluate_vlm_grounding.py --base http://127.0.0.1:<port>/v1 --model <model-alias> --fixture-json <private-frozen-fixture.json> --output <new-private-output-directory>
```

## 共享 4090 上的短时容量探测

默认部署仍要求空闲 4090；新增显式 `shared-4090-probe` 模式用于短时 NF4 诊断，不结束现有服务，也不修改工作台配置。启动前读取实际空闲显存，要求利用率不超过 5%，并留足本进程分配器上限、4096 MiB 余量及 512 MiB 原生上下文估计。每次推理前再次检查余量。分配器上限最多为总显存的 35%，从启动前计时最多 900 秒后本进程自行退出。

分配器限制只约束 PyTorch 分配器，不是整个进程的硬显存隔离。实际 8B 加载后仍须读取本进程 NVML 占用，并核对外部服务和剩余显存；条件不符就终止本次诊断。本轮 8B 已装入预算并完成 23 次真实图片请求；完整 Agent 的两帧均因无变化操作而未收敛，详见下节。

实际机制验证：本机独立进程设置 10% 分配器上限后成功申请 32 MiB，全局空闲显存仍超过 1 GiB 时拒绝额外 1 GiB 申请；无模型加载。另一个新建进程在 30 秒自退出计时后以 124 退出，实测约 31.14 秒。两项均未停止其他进程。这些结果只验证控制机制，不证明远端 8B 推理成功。

190 项完整回归通过，新增图片字节绑定、目录范围、标签不泄露、部分及全不确定结果不能通过、真实后端和图片数、分配器调用顺序、时限及逐请求显存余量检查。

## 8B 的真实对照结果

四份官方权重共 17,534,339,512 字节通过固定版本的官方 LFS SHA256 验证，配置与索引匹配。通过单张 4090、NF4、35% 分配器上限和 900 秒窗口完成了 20 次分类请求及 3 次 Agent VLM 请求；未将该进程设为常驻服务。

第一轮首个请求没有返回：请求线程处于 `rpc_wait_bit_killable`，默认 `.cache` 是网络文件系统上的符号链接。确认故障后仅停止本次进程，检查它确已退出并释放显存，保留失败记录。第二轮为本进程单独指定本地磁盘上的 XDG、Torch、Triton、CUDA 和临时缓存后，20 次请求全部返回有效结果；首个约 14.8 秒，其余请求的整体中位数约 4.219 秒。多项缓存同时调整，尚未逐一隔离具体库的网络读取，不能据此证明此前 SSH 超时也由同一原因造成。

| 同一套输入 | 2B NF4 | 8B NF4 |
| --- | --- | --- |
| 8 个自然裁图：接受/拒绝/不确定 | 1 / 3 / 4 | 1 / 4 / 3 |
| 5 个目视托盘：接受/拒绝/不确定 | 1 / 1 / 3 | 1 / 3 / 1 |
| 空白对照被接受 | 0/2 | 0/2 |
| 疑似非托盘被接受 | 0/1 | 0/1 |
| 全部冻结要求通过 | 否 | 否 |

20 个输入指纹完全相同，14 个单次类别结果发生变化，但 8B 没有增加托盘接受数，反而多误拒两个功能样例。没有采用自动筛选，没有用模型参数规模代替实际改进证据。[对照汇总](vlm_capacity_comparison.json)

## 完整 Agent 的实际失败

按原生产 `workflow.describe/run` 的 compact 模式，用相机 1 第 0 帧的未确认参考，对第 76、151 帧实际生成规范、调用 SAM3 并复核。新增 4 次本机 SAM3 请求、1 次远端规范生成、2 次远端复核，总计约 96.831 秒。两帧生成 11、21 个候选。

8B 两帧均请求将已有 `person` 候选再次分类为 `person`，共 4 个目标，实际编辑 0 次。原有无进展检查以 `no_progress` 停止，两帧均不计为完整成功，也不计为多轮修正。模型的文字声称候选误分类，但对应候选实际已属于人员；这些理由与事实冲突。

两帧候选几何与固定关键词 SAM3 基线相同。冻结预测后由未改动的 V2 单独计分：托盘 3px 实例支持仍为 10/22、点覆盖 526/694，人员仍为 6/6、2301/2466；三档容差的所报指标均无变化。这不是质量提升。[Agent 与指标汇总](vlm_capacity_agent.json)

本轮观测到本进程 NVML 占用约 8356 MiB，低于分配器预算加上下文估计的 9110 MiB；最后一次推理的 PyTorch 峰值分配 8,043,086,336 字节、峰值保留 8,271,167,488 字节。NVML 读数是抽样观察，不是完整峰值记录。测试结束后仅停止本次进程及额外隧道，两卡空闲显存恢复到原观测值，原有三个 GPU 进程仍在。

## 缓存修复与后续范围

新增显式 `--cache-dir <local-disk-private-directory>`，在加载 Torch/Transformers 前设置当前进程的缓存位置，不替换用户原缓存链接，不删除缓存。指定目录中的既有编译文件继续保留；默认不指定时保持原环境。新增三项真实文件系统回归，完整检查为 190 项通过。

Windows 检查须使用启动器同样的 UTF-8 环境及包含 VLM/约束解码依赖的虚拟环境。未设置 UTF-8 的首次检查出现 GBK 解码错误；SAM 环境还跳过 4 项约束解析器测试。改用完整 VLM 环境并启用 UTF-8 后，190 项全部通过，未修改测试以绕过错误。

```sh
python tools/local_vlm_server.py --model-dir <private-model-directory> --gpu-uuid <verified-GPU-UUID> --profile shared-4090-probe --quantization nf4 --cache-dir <local-disk-private-cache> --probe-seconds 900 --max-image-tokens 256 --context-budget 16384 --port 18878
```
