# 自动标注完成回执作用域隔离：Round 219

## 一句话结论

长任务运行期间，如果操作者已经切换数据集、相机、帧或人工/自动工作模式，旧任务完成后现在只会把结果保留在原作用域，不再改写当前页面、候选计数、场景描述或工作模式；用户切回原数据后仍可查看结果。

## 为什么需要这一轮

Round 218 已经保证“开始自动标注”时提交的数据文件和相机不会跑错，但任务提交后可能运行较长时间。旧页面收到完成回执时，会直接执行以下动作：

- 把任务标记为已处理；
- 用旧任务的场景描述覆盖当前描述；
- 更新当前候选计数；
- 把工作模式切回自动标注；
- 尝试打开旧候选。

因此，即使服务端把结果安全保存在原数据作用域，浏览器仍可能把旧回执显示到用户后来切换的新页面上。

## 修复前正式浏览器复现

在生产 v174 的全新 Edge 上执行了可重复竞态，预检和 `/api/run` 完成响应均由浏览器拦截提供，不调用模型、不写候选或人工真值：

1. 从正式 SFL 文件、camera 1、第 74 帧、自动模式提交任务；
2. 暂停 `/api/run` 完成响应；
3. 把页面切到 camera 0、合成另一数据集路径、第 33 帧和人工模式；
4. 放行原任务完成回执，回执带原文件、原相机、旧场景描述和第 10 帧候选计数。

修复前结果：

| 检查项 | 修复前 |
|---|---|
| 当前新数据路径 / camera 0 / 第 33 帧 | 保持 |
| 人工模式 | **被旧回执切回自动模式** |
| 当前场景描述 | **被 `ROUND219_OLD_SCOPE_DESCRIPTION` 覆盖** |
| 第 10 帧候选计数 | **由空改成 2** |
| 旧任务是否被标记为已处理 | **是** |
| 是否保留“稍后查看”入口 | 否 |
| 模型请求 / 真值写请求 | 0 / 0 |
| 页面异常 / 控制台错误 | 0 / 0 |

这证明问题不是服务端把结果算错，而是浏览器错误地把“原任务结果”消费到了“当前新操作作用域”。

## 修复方式

### 1. 提交前冻结完整操作作用域

除 Round 218 已冻结的数据路径、图像源和导航代次外，本轮再冻结提交时的工作模式。预检期间只要人工/自动模式变化，也会取消旧提交。

### 2. 完成回执先核对服务器身份

页面收到 `/api/run` 回执后，先要求回执中的 `file / topic` 精确匹配提交时的文件和相机。任何不一致都直接拒绝，不更新当前页面。

### 3. 区分数据作用域和操作作用域

- **同一数据、同一操作作用域**：正常消费结果；
- **同一数据，但已切帧或切工作模式**：结果保留，显示“查看上次结果”入口；
- **已经切到另一数据集或相机**：结果保存到原作用域，当前页面完全不变，提示切回原数据查看。

旧回执被延后时，不再执行任务已处理标记、场景描述覆盖、候选计数更新、重试状态更新或候选自动打开。
