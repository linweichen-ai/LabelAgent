# Round832–836：本地 Qwen 提示词级联与专家 API 实时复核

## 结论

本轮没有把所有帧交给外部模型，也没有把实验路由部署到正式工作台。当前最值得保留的候选是：

`SAM3 候选复用 → 本地 Qwen 基线复查 → 仅容器口/门口/入口/门槛语境做一次专项 Qwen 复查 → 仍困难才形成外部专家候选`

它在 34 帧机器困难集上，只增加 3 次本地专项复查，而不是对 17 帧全部复查；相对基线的顺序执行估算增加约 56.0 秒，而全量二次复查增加约 122.2 秒。两者对第二助手提出的 11 个斜坡争议都覆盖 9 个，但这仍是机器对机器的覆盖，不是人工准确率。

## 四种本地方案对比

| 方案 | 结果 | 外部候选 | 重点争议覆盖 | 主要问题 |
| --- | --- | ---: | ---: | --- |
| 基线提示词 | 保留作默认基线 | 17/34 | 6/11 | 漏掉部分容器口和画面边缘的局部坡道 |
| V2 容器过渡提示词 | 拒绝 | 34/34 | 11/11 | 过于保守，全部帧升级，失去成本控制意义 |
| V3 严格几何提示词 | 单独使用时拒绝 | 5/34 | 4/11 | 过于严格，作为第一遍会漏掉争议帧 |
| 基线 + 语义选择 V3 | 保留为影子候选 | 19/34 | 9/11 | 外部候选比例仍为 55.9%，且尚无人工真值 |

V2 和 V3 都完整运行了 34/34 帧，没有协议失败。V2 的失败是策略过度升级；V3 的失败是单独使用时召回不足。失败结果和哈希均保留，不能只记录最终候选。

## 语义选择方案如何工作

第一遍沿用稳定的基线提示词。只有本地复查说明明确出现 `container`、`doorway`、`entrance` 或 `threshold` 时，才进行 V3 专项复查。本轮实际只命中 3 帧：

1. 一帧由 `slope=absent` 改为明确的 `slope=present + full_slope`，可作为本地解决候选；
2. 一帧仍为 `slope=uncertain`，继续进入专家候选；
3. 一帧为 `slope=present + partial_edge_slope`，由于是画面边缘局部坡道，仍进入专家候选。

统计口径已改为互斥：局部、遮挡或边缘坡道即使本地说“存在”，也不能同时计为“本地已解决”和“仍需专家”。修正后定向测试 14/14 通过。

最终完整项目回归为 2,036 项通过、1 项跳过、294 个子测试通过。仓库根目录的无约束扫描会误收集 SAM3 自带可视化脚本并要求额外的 `matplotlib`；正式验收限定在项目 `tests/`，同时使用 UTF-8 并排除依赖当前工作树自带 `.venv` 的单个启动互斥环境测试。

## API 接入实时状态

使用程序生成的 512×410 合成图，对已配置的 `openai/gpt-6-astra` 兼容接口做了实时连通测试：

- 请求成功，零重试；
- 延迟 14,722.81 ms；
- 302 个输入 tokens、16 个输出 tokens，总计 318 tokens；
- 没有上传真实工厂图片；
- 没有调用 test24；
- 返回只作为候选验证，不写人工真值。

正式工作台的专家通道仍保持关闭。该测试只证明接口当前可用，不等于混合路由已达到部署门槛。

## 当前限制与下一门槛

1. 34 帧困难集尚无独立人工裁决，9/11 只是相对第二助手候选的机器覆盖。
2. 外部候选仍为 19/34（55.9%），高于期望的经济运行比例。
3. 19 个困难负例中仍有 10 个进入外部候选，本轮没有降低普通地面升级量。
4. 两个未覆盖争议分别来自容器过渡光照变化和门口边缘场景，需要人工确认到底是漏检还是第二助手误报。

下一步应先完成 34 帧盲复核，至少裁决 11 个争议帧；随后以人工结果重新调阈值，比较仅本地、全外部和混合方案的斜坡召回、普通地面误检、延迟与调用比例。在此之前不部署、不训练、不将候选写入真值。
