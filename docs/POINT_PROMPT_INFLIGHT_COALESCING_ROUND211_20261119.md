# 点提示重复请求合并与生产验收：Round 211

## 一句话结论

工作台现在会把“同一数据集、同一相机、同一帧、同一图片字节、同一组点、同一 SAM 地址”的同时重复请求合并为一次真实 SAM 推理，其余请求等待并共享同一结果；不同帧或不同点仍保持互斥，不会串用结果。隔离服务的 6 路并发和正式工作台的 3 路并发均验证为 1 次 owner 推理加其余共享返回，结果核心哈希完全一致。正式人工真值状态、文件会话、模型权重和训练批准均未改变。

## 为什么做这一轮

点提示是人工修边和候选检查中最常用的交互之一。浏览器重复点击、事件重复触发或短时间内的相同重试，旧实现会让第一个请求正常运行、其余请求立即报“已有点提示 SAM 请求正在计算”，用户会感到按钮偶尔失效；如果直接使用长期缓存，又可能在数据集切换或图片变化后错误复用旧结果。

本轮采用更窄的“仅在运行中合并”策略：

- 没有持久缓存，owner 完成后立即删除共享项；
- 请求键同时绑定 SAM 地址、相机 topic、帧号、图片 SHA-256 和完整点数组；
- 只有请求键完全一致才等待并共享；
- 不同点、不同帧、不同图片或不同模型地址继续走全局运行门禁；
- 参考帧仍禁止调用 SAM 自动修改；
- 自动流程运行中仍不能用点提示插队。

## 实现说明

服务端新增一个短生命周期的 in-flight flight：第一个请求是 `owner`，负责在既有全局运行锁和点提示 SAM 锁下调用模型；后到的完全相同请求是 `coalesced_waiter`，只等待 owner 的事件并深拷贝结果。返回值增加 `request_coalescing` 诊断字段：

- `role`：`owner` 或 `coalesced_waiter`；
- `coalesced`：是否共享；
- `wait_seconds`：共享请求等待时间；
- `request_sha256`：精确请求键，便于排查重复触发。

owner 无论成功还是失败都会唤醒等待者并清理 flight；错误只在同一 flight 内传播，不会留下可被后续请求复用的失败缓存。

## 自动测试

新增两类并发回归：

1. 两个完全相同的请求并发时，底层 URL 调用只有一次，两个响应分别为 owner 和 waiter，核心结果一致，flight 清理完成；
2. 第一个请求仍在运行时，第二个不同点请求继续得到 HTTP 503，底层 URL 调用仍只有一次。

同时保留旧的全局运行锁兼容门禁。完整回归在 `PYTHONUTF8=1` 下首次为 **979/979 通过，7.120 秒**；生产部署和文档完成后的最终复验仍为 **979/979 通过，6.982 秒**。生产文件 Python 编译、证据 JSON 解析和差异空白检查通过。第一次未显式启用 UTF-8 的 Windows 运行出现 15 个编码相关失败/错误以及一个已修正的兼容问题，该次不能作为功能回归结论；按项目运行约定启用 UTF-8 后全部通过。

## 用户可感知的改善

过去同一点击被页面重复发出时，用户可能看到一次成功、一次 busy；现在相同请求会一起成功，且只消耗一次 GPU 推理。这个优化不改变分割内容，目标是让手工点提示更稳定、更“丝滑”，并减少重复占用模型槽位。
