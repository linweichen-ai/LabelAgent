# 第二百三十二轮：文件激活代际与“最后一次选择生效”

日期：2026-11-19  
状态：已部署并完成并发单测与正式工作台反向验收  
版本：UI 148、`app.js?v=186`

## 通俗结论

多个页面同时切换数据时，工作台现在会给每次文件选择发一个递增编号。编号较小的旧请求即使后来才完成，也没有资格改服务器或页面；只有最后一次选择能生效。

上一轮只解决了“旧结果不能画到新页面”。这一轮进一步解决“旧请求本身不能成为服务器最终文件”，并覆盖同一路径被重新加载的情况。

## 原问题

单个标签页已有 `fileManagerBusy`，能够避免同页连续点击。但两个标签页、参考帧助手、专项复核入口和旧的打开接口仍可能同时提交文件激活。

服务器原先用一个主锁串行处理，能避免同时写坏状态，却没有记录用户选择先后。如果旧请求正在做较慢的媒体索引或首帧解码，而新请求已经到达，最终次序只能依赖锁和完成时机，不能证明“最后一次选择生效”。

## 修复设计

### 独立的文件激活代际

每个文件激活请求进入服务器时，先通过独立锁取得递增代际。该锁不依赖主状态锁，因此新请求能在旧请求仍做首帧检查时立即登记为最新选择。

旧请求完成媒体检查后、修改任何会话或状态前，必须再次核对代际：

- 仍是最新代际：允许原子切换文件并保存；
- 已被更新请求超过：返回 HTTP 409，不保存旧文件、不触碰候选或人工真值。

文件列表加载、已有标注数据切换、专项复核包激活和兼容 `/api/open` 入口均纳入同一代际。

### 页面同时核对文件、相机和代际

安全加载器现在要求三项全部一致：

1. 文件路径；
2. 相机 topic；
3. 文件激活代际。

这意味着即使两个请求加载的是同一个文件和相机，旧回执也不能利用“路径相同”混入新工作区。相机切换请求也携带页面当前代际；同一路径被另一窗口重新载入后，旧窗口会得到 409，而不是修改新会话相机。

## 可复现并发证据

新增确定性并发测试，人工暂停第一个文件的首帧解码，然后让第二个文件请求进入并取得新代际，再释放第一个请求：

- 第一个旧请求：HTTP 409，错误明确要求以最后一次选择为准；
- 第二个新请求：HTTP 200；
- 服务器最终 `video` 为第二个文件；
- 状态摘要代际与第二个请求完全一致；
- 第一个请求在会话交换和保存之前被拒绝。

因此这不是仅靠页面遮挡旧结果，而是后端状态提交本身具有“最后一次选择”门禁。

## 正式工作台反向验收

部署 UI 148 后，在当前正式文件和 camera 1 上构造“路径、相机都相同，仅代际号落后一代”的回执：

- 安全加载器拒绝旧回执；
- 服务端紧凑相机请求返回 HTTP 409；
- 错误为“数据文件已被重新载入，旧窗口相机请求已拒绝”；
- 文件、相机、代际、8/8 类、44 个候选帧、当前帧16个候选全部保持不变；
- 主图仍可见，页面异常为0。

这比上一轮使用不同伪路径的验证更严格，证明同一路径重复加载也不会把旧窗口当成当前会话。
