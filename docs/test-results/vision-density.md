# 视觉输入密度：真实处理器检查与待执行试验

本页只报告已完成的 CPU 输入处理检查，以及尚未执行的模型对照准备，不把预处理或接口准备当成识别质量结果。

## 实际编码量

使用本机同一 Qwen3-VL-2B 配置和真实已安装图像处理器，核验原局部面板 30 个 JPEG 视图的摘要，分别以每图上限 256、1024 处理。没有加载模型权重，未初始化 CUDA，没有 SAM3/VLM 推理请求，也没有改动原图。

| 输入 | 256→1024 上限后实际编码量增加 | 实际编码量 |
| --- | --- | --- |
| 原生 30 个视图 | 6/30 | 其余 24 个小视图仍为 66～80 |
| 同一组统一采样面积的输入 | 30/30 | 上限 256：224～256；上限 1024：952～1024 |

小裁图只提高最大上限并不会自动增加编码量。另将输入统一重采样到约 1024×32×32 像素面积；同一份 PNG 分别进入两档处理，因此两档看到的源像素字节相同。重采样不增加真实源图细节，部分本已接近该面积的视图也不需要放大。可复现工具完整重做 30 视图后，所有网格与计数逐项一致。[CPU 结果](vision_density_processor.json)

```sh
python tools/inspect_vlm_image_tokens.py --model-dir <local-qwen-model> --fixture-json <private-focus-fixture.json> --output <new-private-output>
```

当前处理器支持这些上限，并不证明 8GB 显卡上真实生成的速度、显存或质量合格；这些仍须新请求确认。此前仅放大至 256 编码预算的真实分类失败结果继续保留，不能由本次 CPU 处理覆盖。

## 已准备的模型对照

已冻结十个未确认功能示例，每例只用单张前景图和单张带轮廓上下文分别询问；不同于旧面板的三图上下文。两策略分别请求 256、1024 编码预算，共计划 40 次真实单图请求，当前完成 0 次。两策略的图片字节、提示、schema、温度与输出预算相同，顺序交错。

每个响应必须证明真实 CUDA/NF4、配置摘要相同、只接收一张图、实际请求预算正确，并提供与真实处理器事先计数相等的视觉编码量。当前服务代码只有进程级上限，尚未验证支持请求级覆盖；在服务明确支持和返回这些证据前，工具应停止，不能把未知参数被忽略误算为已执行 1024 对照。

预设要求仍包括空白与疑似反光不被接受、人员视图正确、至少三个托盘示例两视图一致且不把托盘判成人员。面板是助手构造的未确认功能示例，不是独立人工二维真值；通过也不能直接安装通用过滤或宣称数据集准确率提高。先检查实际显卡资源，保留其他任务，默认工作台 256 配置和原始标注保持。[计划及未执行状态](vision_density_plan.json)
