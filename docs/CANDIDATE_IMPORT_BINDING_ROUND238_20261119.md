# 第二百三十八轮：外部候选导入与合并的状态强绑定

日期：2026-11-19

状态：已部署并完成全量回归、正式 HTTP 反向验收、备份和双远端同步

工作台版本：UI 152、`app.js?v=190`（本轮未改前端）

## 通俗结论

工作台支持把外部程序生成的分割候选导入进来，但旧接口只检查“是不是同一个文件路径”。如果同一个 MCAP 被重新载入、相机已经切换，或者人工真值、类别、现有候选已被另一流程更新，旧工具仍可能把基于旧状态生成的结果写进新会话。

现在外部候选写入必须携带一张完整的“状态指纹”：文件、相机、载入代次、类别状态、全部人工真值基线和全部机器候选基线。任一项变化，导入或合并都以 HTTP 409 停止，不写候选、不碰人工真值。

## 本轮实现

### 1. 统一候选导入绑定

bootstrap 和文件载入回执新增 `candidate_import_binding`：

- `path`：当前数据文件；
- `topic`：当前图像相机；
- `file_activation_generation`：当前文件载入代次；
- `label_state_sha256`：项目类别和推理类别状态；
- `truth_state_sha256`：当前相机及所有暂存相机的人工真值状态；
- `candidate_state_sha256`：当前相机及所有暂存相机的机器候选状态。

跨相机状态先规范化为同一按 topic 组织的结构再计算 SHA-256，避免当前相机与暂存相机存储方式不同导致漏检。

### 2. 导入和按类别合并共用同一门禁

`/api/candidates/import` 与 `/api/candidates/merge` 在同一把主状态锁内：

1. 检查工作台没有运行任务；
2. 核对路径、相机和载入代次；
3. 核对类别、人工真值和候选三个状态哈希；
4. 验证所有输入话题、帧号、类别和几何；
5. 只在全部通过后更新候选并持久化。

成功回执同时返回：

- `applied_binding`：实际应用前的精确绑定；
- `candidate_import_binding`：写入后的新绑定；
- `input_sha256`：本次输入候选（合并时还包含授权类别）的哈希；
- `saved_as_truth: false`。

因此调用方能够证明自己写入的是哪一个基线，并获得下一次写入必须使用的新基线。

### 3. 官方导入工具同步升级

`tools/load_candidates.py` 在载入文件后读取服务端返回的绑定，检查字段完整性，再提交候选。写入成功后还要求 `applied_binding` 与载入时绑定完全一致；任何字段缺失或变化都会停止，不以“请求返回200”代替状态一致性验证。
