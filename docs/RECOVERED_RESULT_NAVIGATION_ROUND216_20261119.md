# 历史候选恢复尊重用户导航：Round 216

## 一句话结论

工作台恢复上次自动标注结果时，如果用户主动切到另一帧，系统现在会保留用户选择、保留“查看上次结果”入口，并停止后台自动抢回候选帧；只有用户明确点击查看且候选帧确实打开成功后，才把该任务记为已处理。

## 修复前的问题

页面刷新或后台任务完成后，会读取持久化结果并尝试打开第一个有候选的帧。Round 214 已保证较新的用户跳帧不会被旧导航覆盖，但恢复函数没有检查候选帧是否真的打开成功：

1. 系统尝试恢复第 10 帧；
2. 用户在读取期间主动选择第 20 帧；
3. 页面正确停在第 20 帧，第 10 帧打开被取消；
4. 恢复函数仍把任务加入 `runResultHandled`；
5. “查看上次结果”按钮消失，变回“开始自动标注”。

这样候选数据虽然仍在服务器上，但用户失去了清晰的恢复入口。

## 修复前正式 Edge 复现

在 v170 正式页面，用浏览器拦截提供一个只读测试结果：任务第 10 帧有 1 个候选。第一次时间轴读取延迟 500 ms，用户 20 ms 后选择第 20 帧，第二次读取仅延迟 50 ms。

| 项目 | 修复前结果 |
|---|---|
| 页面最终帧 | 20，尊重了用户最后导航 |
| `recoverRunResult()` 返回 | `true` |
| 任务是否被记为已处理 | **是** |
| 是否仍可恢复 | **否** |
| 按钮 | “开始自动标注” |
| 人工真值写请求 | 0 |
| 模型分割请求 | 0 |

即“显示没有被抢回”已经成立，但“结果恢复状态”仍然错误。

## 修复方式

### 1. 候选打开返回真实成功状态

`openCandidateFrame()` 不再只要函数走完就返回候选状态。它要求：

- `showFrame()` 明确返回成功；
- 当前帧仍等于目标帧；
- 当前相机仍等于结果相机。

三者同时成立才返回 `true`。

### 2. 只有实际打开后才标记已处理

若候选打开被新的用户导航取消：

- 不加入 `runResultHandled`；
- 任务仍保持 `result_available=true`；
- 按钮继续显示“查看上次结果”；
- 页面提示结果已保留，没有丢失。

### 3. 自动恢复退让，人工点击重新授权

被用户导航取消过的任务加入当前浏览器会话的“自动恢复暂缓”集合。后续低频状态轮询不会再次请求结果、不会每隔几秒抢回候选帧。用户点击“查看上次结果”时会清除暂缓并重新尝试；成功打开后才完成处理标记。

暂缓状态仅存在浏览器内存，不修改服务器结果，也不会影响刷新后再次恢复。

### 4. 不误改新任务状态

恢复响应回来时，只有全局当前任务 ID 仍与该结果 ID 一致，才更新全局 `result_available`。如果期间出现更新任务，旧恢复不会改写新任务状态。
