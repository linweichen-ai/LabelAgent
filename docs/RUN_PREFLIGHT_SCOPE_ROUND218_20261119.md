# 自动标注预检期间作用域切换防护：Round 218

## 一句话结论

点击“开始自动标注”后，如果模型/数据预检尚未结束时操作者切换了帧、相机或数据集，工作台现在会取消旧提交并要求在当前画面重新开始；正常提交同时携带原数据文件和原相机，服务端会再次核对，避免另一标签页在最后一瞬切换全局数据后跑错对象。

## 审计起点

Round 217 后首先检查了参考场景描述生成。服务端在保存描述前已经重新核对数据对象、文件路径、相机、配置、标签表、自动标签、参考帧集合、参考真值和参考签名；变化时会拒绝保存旧描述。因此没有发现旧描述跨数据集落盘的问题。

继续检查自动标注启动链路时发现：页面先记录起始帧，再并行等待模型、参考流程和首帧数据兼容检查，最后才调用 `/api/run`。旧请求体只有帧号、数量和复查轮数，没有原文件和原相机；预检期间的页面导航也没有在提交前复核。

## 修复前正式浏览器复现

正式 v173 使用全新 Edge 上下文，所有预检与 `/api/run` 均由浏览器提供合成响应，不调用模型：

1. 在 SFL camera 1 第 74 帧点击自动标注；
2. 暂停模型就绪响应；
3. 等待期间把页面作用域切到 camera 0、合成新数据集路径和第 33 帧；
4. 放行预检；
5. 页面仍提交 `/api/run`，请求帧为旧第 74 帧。

旧请求体为：

```json
{
  "frame": 74,
  "count": 1,
  "max_rounds": 2,
  "defer_agent_review": false,
  "compare_with_truth": false
}
```

| 项目 | 修复前结果 |
|---|---|
| 预检开始作用域 | camera 1、第 74 帧、正式 SFL 文件 |
| 提交时页面作用域 | camera 0、第 33 帧、另一数据路径 |

真实服务端若在这个窗口切换全局数据，旧第 74 帧可能被解释为新相机/新数据集中的第 74 帧。

## 修复方式

### 1. 浏览器在预检前冻结原作用域

开始预检时记录：

- 数据文件路径；
- 图像相机；
- 起始帧与处理范围；
- 单调导航代次。

预检结束后，只要数据集、相机或导航代次发生变化，就不再发送 `/api/run`，并提示：

> 预检期间数据集、相机或当前帧已经切换，本次自动标注未启动；请在当前画面重新开始

### 2. 正常请求携带强绑定

正常单帧、连续多帧和失败重试请求统一增加：

```json
{
  "expected_file": "发起预检时的数据文件",
  "expected_topic": "发起预检时的图像相机"
}
```

### 3. 服务端做第二层核对

服务端在读取参考帧、描述或启动模型前，先比较 `expected_file / expected_topic` 与当前加载状态。字段只给一个会返回 HTTP 400；两者完整但任一不匹配会返回 HTTP 409，且不会启动任务。

保留未携带新字段的旧 API 调用兼容性；正式 v174 页面始终携带两项绑定。这样既避免缓存旧页面突然不可用，也让当前页面与服务端共同防护跨标签页竞态。
