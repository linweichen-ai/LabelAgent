# Round811：Astra 合成图分辨率与用量矩阵

## 目的

本轮只验证外部专家输入分辨率对 token 用量和请求延迟的影响。所有请求均使用程序生成的合成图，没有上传工厂图片、标注、路径或 `test24` 数据。合成测试不评价真实场景识别质量，因此不能直接据此降低正式输入分辨率。

## 首轮四档结果

| 分辨率 | 输入 token | 输出 token | 总 token | 延迟（ms） |
|---|---:|---:|---:|---:|
| 640×512 | 23,316 | 12 | 23,328 | 13,065.804 |
| 512×410 | 302 | 16 | 318 | 3,219.150 |
| 384×307 | 197 | 16 | 213 | 5,157.710 |
| 320×256 | 149 | 16 | 165 | 3,050.883 |

首轮显示 640×512 与较小尺寸之间存在异常大的 token 跳变。为避免把偶然值当成结论，本轮又独立重复了 640×512 和 512×410。

## 重复结果

| 分辨率 | 输入 token | 输出 token | 总 token | 延迟（ms） |
|---|---:|---:|---:|---:|
| 640×512 | 23,316 | 12 | 23,328 | 13,600.101 |
| 512×410 | 4,415 | 16 | 4,431 | 5,246.517 |

640×512 在三次独立调用中均为 23,328 总 token，表现稳定；512×410 两次分别为 318 与 4,431 token，说明网关的 token 回执或内部图像处理存在明显波动。即使取较高的 4,431，仍比 640×512 少约 81%。延迟也从约 13秒降到约3.2～5.2秒。

因此目前只能得到两个工程候选结论：

1. 640×512 可能触发了明显更昂贵的图像编码路径；
2. 512×410 值得进入真实开发困难集的受控 A/B，但尚不能部署，也不能证明斜坡、托盘和小目标质量不下降。

384×307 和 320×256 各只有一次合成测试，且过低分辨率很可能损失边缘局部斜坡、小目标和遮挡信息，暂不作为优先真实 A/B 尺寸。

## 新增工具

- `tools/expert_vlm_smoke.py` 支持128～2048范围内的合成图尺寸；默认640×512行为和原哈希保持不变。
- `tools/expert_vlm_resolution_matrix.py` 支持一次比较2～6个唯一尺寸，记录 token、延迟和合成图哈希。
- 输出强制声明 `quality_evaluated=false` 与 `deployment_recommendation=false`，避免把成本测试误写成质量提升。
- 供应商名称现在从每次规范化后的 smoke 回执读取，历史 UI 别名不会继续污染新矩阵报告。

## 下一门槛

获得真实开发帧外发授权后，在同一批人工复核困难帧上比较 640×512 与 512×410：

- 斜坡正例召回与普通地面误检；
- 托盘数量、孔洞、粘连与小目标召回；
- 类别冲突；
- 平均/P95延迟；
- token用量和成本。

只有质量不下降且用量/延迟稳定改善时，512×410才可进入混合路由候选配置。
