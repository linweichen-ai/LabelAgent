# 第二百二十四轮：失败重试绑定来源任务，防止旧标签页覆盖新候选

日期：2026-11-19  
状态：已实现、已全量回归、已部署到正式工作台并完成浏览器验收

## 通俗结论

以前页面记住“哪些帧失败了”，只记数据文件和相机，没有记住这份失败清单来自哪一次任务。极窄但真实的多标签页窗口是：旧标签页保留“重试第 1 帧”，另一标签页已经完成更新任务；旧页仍可把旧清单重新提交，服务端会再次推理，并可能覆盖较新的机器候选。

现在失败/中断重试必须携带产生这份清单的任务号。服务端会在启动模型前确认：它仍是当前最新结果、文件和相机一致、请求帧仍在该任务的失败或未完成清单中。任一条件不符即返回 HTTP 409，模型不启动、候选不改变；页面清除过期重试清单并自动读取最新结果。

## 修改内容

### 1. 重试清单保存来源任务号

页面从运行结果恢复失败帧或未完成帧时，同时保存：

- 数据文件；
- 相机 topic；
- 来源任务号 `taskId`；
- 失败/未完成帧清单。

直接运行回执产生失败帧时，也使用本轮回执的 `task_id`。没有合法任务号的旧内存清单不再被当作可提交重试。

### 2. 浏览器提交前再次核对

点击重试时先冻结当前失败帧和来源任务号。模型、流程和数据预检完成后，再确认页面的重试来源没有被新状态刷新替换；只有仍一致才提交：

`expected_result_task_id=<来源任务号>`

这样预检期间发生的新任务也不会被旧点击穿透。

### 3. 服务端成为最终门禁

服务端收到显式 `frames` 重试时：

1. 缺少来源任务号返回 HTTP 400；
2. 读取当前持久化运行摘要；
3. 要求任务号、文件和相机与来源完全一致；
4. 要求每个请求帧仍属于 `failed_frames` 或 `pending_frames`；
5. 任何过期或不匹配返回 HTTP 409；
6. 所有核对通过后才进入模型推理。

因此即使浏览器状态刚好过期，服务端仍能阻止旧重试覆盖较新候选。

### 4. 过期后的自动恢复

页面收到 409 后会：

- 清空旧失败/未完成清单；
- 解除“正在提交”锁；
- 立即刷新运行状态；
- 自动读取较新的运行结果；
- 不反复重试旧任务。

HTTP 错误对象现在保留状态码和结构化回执，页面可以只对明确的 409 竞态执行上述恢复，其他错误仍按原方式报告。
