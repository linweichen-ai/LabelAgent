# Round514：人工签字导入门禁攻击复核与收口

## 为什么需要这一轮

Round513 已能识别完整人工签字，但“正常输入能通过”不等于异常路径安全。本轮让 WorkBuddy 在隔离环境只读审计，再由主线独立复现与修复。审计没有读取 test24、真实签字、图片或凭证，也没有训练、改真值或推送。

## 已复现的问题

1. 私有输出和公开回执若指定同一新路径，旧实现会先写私有结果、再被公开回执覆盖，进程仍返回成功。
2. 第二份输出写失败时，第一份私有结果可能残留；“检查不存在再写入”还存在并发创建后被覆盖的窗口。
3. 私有输出原先允许写到仓库外任意位置，容易把候选ID、签核人和逐行结果散落到非私密目录。
4. CLI 未捕获异常时，traceback 可能包含本机敏感路径。
5. 输入 JSON 的解析与 SHA-256 原先分两次读取；并发替换文件时，解析内容和记录哈希可能来自两份不同字节。
6. 行内夹带 `training_authorized=true` 会被忽略；虽然旧输出仍是未授权，但输入语义自相矛盾。

## 已完成修复

- 两个输出路径必须不同；输出采用排他创建，永不覆盖已存在文件。
- 两份内容先在内存中固定；第二份写入失败会回滚本轮刚创建的第一份，避免半成品。
- 私有输出强制位于仓库 `.repro/`，公开回执仍只含安全汇总。
- CLI 把校验失败和I/O失败转换为无路径、无traceback的短错误。
- 每个输入只读取一次原始字节，同一份字节同时用于 JSON 解析和 SHA-256；输入上限固定为4 MiB。
- 行级训练批准注入被拒绝，完整签字的 `human_signoff_count` 必须与81项一致。

## 验证结果

- 导入器定向测试24项通过；连同签字模板与时序门禁，共28项通过。
- Python 编译检查与 Git 差异检查通过。
- 使用真实空白签字模板运行 CLI：退出码2，只输出安全拒绝原因，私有输出与回执均未创建。
- 当前仍没有真实人工签字：`human_signoff_count=0`、`training_authorized=false`、`automatic_approval=false`。

## 尚未声称解决的边界

复核人仍是 JSON 中的声明身份，尚无账号认证或数字签名。因此本轮证明的是“导入器不易被异常文件和路径绕过”，不是“签字人身份已经密码学可信”。在接入身份认证或签名密钥前，训练授权继续保持关闭。
