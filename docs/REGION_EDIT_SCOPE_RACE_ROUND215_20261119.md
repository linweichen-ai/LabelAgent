# 人工区域编辑跨帧污染防护：Round 215

## 一句话结论

“添加区域”和“擦除区域”的异步结果现在严格绑定提交时的数据集、相机、帧、工作模式、轮廓序号和原始轮廓内容。修复前可稳定复现：第 74 帧提交区域编辑后切到第 20 帧，旧结果会覆盖第 20 帧刚选中的草稿；修复后旧结果被明确丢弃，同一帧正常编辑仍可应用，连续两次编辑只采用最后一次。

## 问题是什么

区域编辑会把用户绘制的多边形和当前轮廓发给本地服务计算合并或擦除。旧实现等待返回后，直接执行：

`selectedShapes()[selectedShapeIndex] = result`

这里读取的是“返回那一刻”的当前帧和当前选中序号，而不是“提交那一刻”的帧和轮廓。因此：

1. 用户在第 74 帧选择轮廓并提交添加区域；
2. 服务仍在处理时，用户切到第 20 帧并选中第一个轮廓；
3. 第 74 帧的旧结果随后返回；
4. 旧代码把它写到第 20 帧的第一个内存草稿上。

该草稿不会自动成为人工真值，但页面会显示错误轮廓；如果用户没有发现并继续人工保存，就存在误操作风险。

## 修复前真实浏览器复现

使用正式 v169 页面和全新 Edge 上下文，浏览器拦截 `/api/edit_region` 并延迟 600 ms。拦截只返回内存测试轮廓，不调用真实几何服务，也不写服务器状态。

| 项目 | 结果 |
|---|---|
| 提交帧 | 74 |
| 等待期间切换到 | 20 |
| 第 20 帧原草稿类别 | `DESTINATION_FRAME_SHAPE` |
| 旧响应类别 | `STALE_REGION_RESULT` |
| 修复前第 20 帧最终类别 | **`STALE_REGION_RESULT`** |
| `staleEditOverrodeDestination` | `true` |
| 人工真值写请求 | 0 |
| 页面异常 | 0 |

这证明问题是页面作用域竞态，不是 SAM/VLM 精度或服务端数据错位。

## 修复方式

每次区域编辑提交时冻结：

- 区域编辑代次；
- 数据集路径；
- 相机 topic；
- 帧号；
- 人工/自动工作模式；
- 轮廓序号；
- 原轮廓的完整稳定快照；
- 编辑类型和绘制多边形的深拷贝。

结果返回后必须同时满足：

1. 仍是最新一次区域编辑；
2. 数据集、相机、帧和工作模式均未改变；
3. 原轮廓仍位于同一序号且内容未变。

任一条件不满足，结果只提示“已安全丢弃”，不修改任何草稿。若轮廓在提交前已经不存在，也会在发请求前提示重新选择，不产生无效请求。
